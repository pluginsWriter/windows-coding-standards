# 设计粒度判据：臃肿与过度拆分

> 版本：v0.1.1 · 2026-09-28
> **本文件是判据层，跨语言共享。** C++ 与 C#/.NET 两侧共同引用它。
> **但检测命令分语言** —— 本文件只给判据与"该由谁检查"的索引，具体命令见两侧正文。
> 成因与动机见 §0；判据见 §2–§4；检测见 §6。
>
> **同族文件**：`change-discipline.md` 管的是**改动本身**（整改不得改行为、不得堆代码），
> 本文件管的是**代码形状**（臃肿 / 拆碎）。两者必须同时生效：只防拆不防加 → 代码膨胀；只防加不防拆 → 结构失控。
> 分工对照见 `change-discipline.md` §2.5。

---

## 0. 为什么单列一份

**因为过去两侧都只设了上限，没有下限。**

- 上限（函数行数、类型行数、复杂度）有数值，好写好查；
- **下限（"拆得太碎"）没有任何条目** —— 而它恰恰是 AI 生成代码最常见的形态。

AI 的边际成本为零，所以它倾向于：

| AI 的零边际动作 | 结果 |
|---|---|
| 见一个类型就建一个文件 | 文件数暴涨，类型间关系不可见 |
| 见一个接口就建一个抽象 | 单实现接口、单继承抽象类 |
| 见一个功能就建一个 `XxxManager` / `XxxService` | 无状态转发层，调用链被拉长 |
| 见一段逻辑就抽一个私有方法 | 函数被切成 3 行一段的碎片，读一遍要跳 8 次 |
| 见一个测试点就拆一个函数 | 为"可测试性"而拆，不是为职责而拆 |

**这些都不会被任何检查器报出来** —— 因为它们形式上完全合规：行数没超、复杂度没超、命名没违规。

> **另一侧的代价**：只盯上限会通往另一个极端 —— 把 800 行的方法硬拆成 13 个小方法，每个都没有独立含义，读者需要在 13 个定义之间跳来跳去才能拼出一次完整的业务流程。**这比一个 800 行的长方法更难维护。**
>
> 判据不在行数里，在**改动边界**里。

## 1. 两个方向必须同时查

| 方向 | 可定量性 | 处理 |
|---|---|---|
| **上限：臃肿** | 可定量、有工具 | 进 CI，给数字 |
| **下限：过度拆分** | **不可定量为违规**（行数短不是违规） | 只能**给判据 + 人工评审**；可 grep 的只是"候选信号" |

**这是本文件存在的全部理由**：把"下限"从"没人管"变成"有判据、有评审清单、有候选筛选命令"。

**禁止的做法**：给碎片化定一个数值阈值（如"单文件 < 30 行即违规"）。那会立刻误伤：**合法的值类型、强枚举、接口声明天然就短**。阈值可以把候选筛出来给人看，**但不能作为违规判定**。

## 2. 上限：体量阈值（由各语言自己的配置承载）

| 项 | C++ 侧载体 | C#/.NET 侧载体 |
|---|---|---|
| 圈复杂度 / 认知复杂度 | `.clang-tidy` 的 `readability-function-cognitive-complexity.Threshold`（**等级 SHOULD**，理由见 C++ 正文 §5.4） | `CA1502`（内置；阈值配置键名 `[待实测]`） |
| 函数行数 | `readability-function-size.LineThreshold` | 无内置规则 → SHOULD + 人工 |
| 类型行数 | 无工具 → SHOULD + 人工 | 无内置规则 → SHOULD + 人工 |
| 参数个数 | `readability-function-size.ParameterThreshold` | `CA1026` 相关 / 人工 |
| 嵌套深度 | `readability-function-size.NestingThreshold` | 无内置规则 → 人工 |

> **有配置载体的取值（C++ 侧这五项）只写一份** —— 权威是 `assets/clang-tidy`，本文件与两侧正文都**不复制数值**。
> **没有载体的取值（C# 侧四项：圈复杂度 / 函数行数 / 类型行数 / 参数个数）以 C# 正文 §5.3 为唯一出处**，本文件同样不复制。
> 上表只是"哪一项由谁检查"的索引。

**触发上限之后该怎么办**：见 §3。**超过上限不等于必须拆** —— 先过判据。

## 3. 下限：拆分的正当理由（**本文件的核心**）

### 3.1 唯一判据

> **拆分出的每一个单位，必须有一个能独立说出口的变化原因。**

不是"这段代码有点长"，不是"这样更清晰"，不是"便于测试" —— 而是：

> **「当 ______ 变化时，我只改这里，不用碰那边。」**

这句话填不完整，就不该拆。

### 3.2 提问清单（拆分前逐条问，有一条答不上就别拆）

| # | 问题 | 答不上来的含义 |
|---|---|---|
| 1 | **谁调用它？有几个调用方？** | 只有一个调用方且无第二个的计划 → 拆是为了"好看" |
| 2 | **我改 A 功能时，会不会被迫碰 B？** | 会 → 两者本就不该分在两个单位里 |
| 3 | **把它的内容搬回原处，代码会变长，还是会变得更难懂？** | 只是变长 → 别拆 |
| 4 | **能用一句话说清它负责什么，且句中不含"和""以及""同时"吗？** | 含 → 它其实是两件事，或它什么都没负责 |
| 5 | **它有自己的状态吗？** | 无状态 + 只含一个转发函数 → 多半是多余的间接层 |
| 6 | **它有几个实现 / 子类？** | 只有一个，且无第二个的具体计划 → 抽象是提前的 |
| 7 | **这个边界在未来会变吗？** | 不会变 → 为假想的变化付出真实的复杂度 |

### 3.3 允许拆的信号（拆是正当的）

1. **两个变化原因确实独立** —— 例如"协议格式"与"传输方式"，任一变化不需要动另一个。
2. **同一逻辑有 ≥ 2 个真实实现**（不是"将来可能有"）—— 有第二个实现者，抽象才有对象。
3. **有必须被隔离的边界**：平台差异、第三方依赖、测试替身、ABI 边界。
4. **单位可独立测试且测试本身有独立价值** —— 注意：**"可测试性"只有在测试验证的是不同的契约时才算独立价值**；把一个大函数切成 5 个只为各写一个测试，是假价值。
5. **明确的所有权 / 生命周期边界** —— 例如资源持有者与使用者分离（C++ 侧尤其常见）。

### 3.4 禁止拆的信号（拆是有害的）

1. **只是"这段有点长"** —— 长度不是理由（§3.1）。
2. **为复用而拆，但只有一个调用点** —— 复用需要一个真实的第二次使用来证明。
3. **为可测试性而拆，且拆出的单位契约与原处相同** —— 测试点变多了，被验证的契约没变。
4. **无状态的单方法类** —— `XxxHelper::Process()`、`XxxUtils::Format()`；它通常应当是自由函数，或根本不需要存在。
5. **接口与实现 1:1 且无第二个实现的计划** —— 这是 C++/C# 两侧都最常见的过度抽象。
6. **类型名与它唯一的方法名同义** —— `OrderValidator` + `Validate()`，说明这个类型没有承载任何额外语义。
7. **抽出的名字比被抽出的代码更费解** —— 提取后需要注释解释"这个函数干什么"，说明提取点选错了。

### 3.5 碎片化的可观测症状（用于人工评审时的对照）

这些**不是违规判定**，是把注意力引到正确位置的信号：

| 症状 | 说明什么 |
|---|---|
| 单文件只含一个类型且很短 | 文件边界与职责边界脱钩 |
| 大量 `XxxManager` / `XxxHelper` / `XxxUtils` / `XxxService` | 职责没想清，用后缀兜底（见 `cpp-naming-antipatterns.md` §1 E） |
| 调用一个业务流程要跨 5 个以上文件 | 分散程度超过了理解能力 |
| 类型总数增长快于功能增长 | 抽象在提前消费 |
| 私有方法平均不足 5 行 | 提取点选择不当 |
| 每个小类都有一个对应的测试文件 | 测试在验证实现形状，而不是行为 |
| 删除某个中间类型后调用链反而更清晰 | **该类型是净负债** |

最后一条是最有用的检验：**如果一个中间环节删掉后代码更好懂，那它本就不该存在。**

## 4. 上限触发时的正确动作

**上限是"提示需要检查"，不是"必须拆"。**

```
超过阈值
   ↓
过 §3.2 的提问清单
   ↓
├─ 能说出独立变化原因 → 按该原因拆，并把这个原因写进提交信息
└─ 说不出            → 不拆；改为在类型/函数头部写明它的职责与不变式（§5）
```

**禁止**：为了把行数压到阈值以下而机械切割。**那只会把"难以理解的大段"变成"难以理解的多段"。**

## 5. 拆解之后：类型级设计意图（让拆解可理解）

拆解会**天然增加**读者的认知负担 —— 补偿它的唯一办法是把设计意图写下来。

**要求（两侧一致）**：每个对外类型，在其声明处说明三件事：

1. 这个类型**为何存在**（它负责的单一职责）
2. 它**与谁协作**（依赖谁、被谁持有、生命周期由谁管）
3. 它**不负责什么**（边界，防止职责蔓延）

**为什么这条是"设计逻辑难懂"的真正解药**：成员级文档再齐全，也回答不了"为什么有这个类、它和旁边那个类的区别是什么"。**读者需要的是地图，不是每个地标的说明牌。**

**载体两侧不同**（不得互抄）：

| | C++ | C#/.NET |
|---|---|---|
| 语法 | Doxygen：`/** @brief */` `///` | XML：`/// <summary>` `<remarks>` |
| 强制手段 | **无对等开关** → SHOULD + 人工 | 有 `CS1591`（只查存在性）→ 但**不查设计意图** |
| 落点 | 类型声明的头文件处 | 类型声明处 |

> ⚠️ **即使有 `CS1591`，它也只查"有没有 `<summary>`"，不查有没有说清设计意图。** 在 C# 侧，"补一个同义复述的 `<summary>`"既满足了检查、又完全没有传达设计意图 —— 这是规范自己制造的假达标。判据是**内容**，不是标签存在。

## 6. 检测：哪些能机器化，哪些不能

| 项 | 能否机器化 | 说明 |
|---|---|---|
| 臃肿（行数 / 复杂度 / 参数） | ✅ 部分 | 见 §2 的载体表 |
| 类型行数 / 嵌套深度 | ⚠️ 无内置规则 | 自建脚本或人工 |
| **碎片化** | ❌ **不能判定** | 只能给候选信号；**判定必须人来做** |
| 类型级设计意图 | ❌ | 语义 |

### 6.1 碎片化的候选筛选（**候选，不是结论**）

以下是筛选"值得看一眼"的命令。**输出的是候选清单，不是违规清单** —— 每一条都要人过 §3 的判据。

```bash
# 【通用】单文件只含一个类型且很短（< 30 行）—— 碎片化候选
# 注意：`[[:space:]]` 不能用 `\s`（BSD grep 不支持，会静默失配）；
#       判据必须写成 n>=1 且 n<=1 —— 只写 n<=1 时，模式失配导致 n=0 会全量误命中。
find . -name '*.cs' -exec sh -c 'n=$(grep -cE "^[[:space:]]*(public|internal)[[:space:]]+(sealed[[:space:]]+)?(class|interface|record|struct)" "$1"); l=$(wc -l < "$1" | tr -d " "); [ "$n" -ge 1 ] && [ "$n" -le 1 ] && [ "$l" -lt 30 ] && echo "$1 ($l 行)"' _ {} \;

# 【通用】无状态的 Helper / Utils / Manager 类 —— 职责不明的信号
grep -rnE 'class [A-Za-z]*(Manager|Helper|Utils|Common|Service)\b' --include='*.cpp' --include='*.h' --include='*.cs' . | head -30

# 【C++ 专用】接口与实现 1:1 候选（列出所有含纯虚函数的类，人工比对实现数）
grep -rnE '=\s*0\s*;' --include='*.h' --include='*.hpp' . | head -30

# 【C# 专用】单实现接口候选
grep -rnE 'class [A-Za-z0-9_]+ *: *I[A-Za-z0-9_]+' --include='*.cs' . | head -30
```

> **上述命令的已知局限（实测）**：
> - 类型计数模式**不认 `partial` 关键字** → `public sealed partial class X` 会数成 0 个类型。判据里的 `n >= 1` 保护就是为了防止这个 0 变成全量误命中。
> - C++ 侧**无法可靠地用文本匹配区分"接口"与"抽象基类"**（宏、模板特化、`= 0` 的各种写法），因此 C++ 的接口候选命令只能作粗筛。
> - macOS 的 `awk length()` 按**字节**计（中文一个字算 3 字节），不要用它做字符阈值。

## 7. 针对 AI 生成代码的三个额外提醒

1. **AI 会 100% 遵守机器规则，然后生产机器规则查不出的东西。** 碎片化、过度抽象、样板间接层都在此列。**"检查全绿"不是设计合理的证据。**
2. **AI 倾向于"对称拆分"** —— 看到三个操作就创建三个文件，即使它们的生命周期与变化原因完全绑定。**拆分的依据是变化原因，不是数量对称。**
3. **AI 倾向于"防御性拆分"** —— "以防将来需要"。**将来不需要的证据，比"将来可能需要"的猜测更有价值。** 拆分是可逆的，但错误的拆分留下的复杂度是持续的。

## 8. 评审清单（可直接用于 code review）

- [ ] 本次新增的每个类型，能否一句话说清职责（不含"和"）？
- [ ] 新增的每个抽象 / 接口，有几个实现？若只有一个，第二个在哪？
- [ ] 新增的每个文件，与它所在类型的职责边界是否一致？
- [ ] 新增的每个私有方法，是否有一个能独立说出口的名字（而不是 `ProcessStep1`）？
- [ ] 改动的类型是否写了类型级设计意图（§5）？
- [ ] 有没有"删掉会更清晰"的中间环节？
- [ ] 本次是否引入了为假想需求准备的抽象？
