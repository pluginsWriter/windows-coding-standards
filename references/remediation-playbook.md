# 整改手册：把这套规范接入存量工程的操作纪律

> 版本：v0.1.0（自接入计划落地为判据层；**本文不写任何阈值取值** —— 取值的唯一权威是各侧正文与 `assets/` 模板，本文只给指针）· 2026-09-29
> 状态：**跨语言判据层**，两侧共用；侧特定命令以表格分列，互不套用（给 C++ 代码跑 `dotnet format` = 已经跑错了一侧）。
> 硬约束的唯一出处是 `change-discipline.md`；粒度判据的唯一出处是 `design-granularity.md`；本文只管**操作顺序与交付纪律**。

---

## 0. 为什么单列一份

两侧正文说的是"合格长什么样"（判据），本文件说的是"**怎么走到合格而不把工程改坏**"。
没有它，接入就只剩两种失败形态：要么一次巨量 diff 无法评审，要么"整改"变成顺手重构 —— 病没治，行为先变了。

## 1. 两条不可协商的约束

1. **整改不得改变原有行为**（接入存量代码之前）—— 判据与八项"行为"清单见 `change-discipline.md` §1。
2. **不得为满足规则而增加代码**（接入之后）—— 判据与正当新增清单见 `change-discipline.md` §2。

这两条**优先于本文件的任何流程步骤**：流程与约束冲突时，改流程，不改约束。

## 2. 阶段总览

| 阶段 | 内容 | 出口条件 |
|---|---|---|
| **P0** | 冻结范围、判定语言、盘工具、盘测试 | 工具齐、测试基线有记录（没测试的工程记"只做 A 类"） |
| **P1** | 工程现状基线（**只读**） | 「N 处 / M 文件」数字落盘，分母可复现 |
| **P2** | 回滚点 → 安装配置 → 对照实验 → 可信基线 | 注入的已知违规**全被报出**；可信基线落盘 |
| **P3** | 分层整改（本文件核心） | 每层前后数字可比、逐处挂缺陷编号 |
| **P4** | 开闸（钩子与 CI，只读检查） | 注入违规被**拦下**而不只被报出 |
| **P5** | 交付与验收 | 交付四件齐（见 §8） |

**顺序不能反**：没建回滚点就装配置、没做对照实验就信"0 违规"、没盘测试就动 B/C 类 —— 都是后面清单里的假绿。

## 3. P0：先证明"检查工具链本身是活的"

- **判定语言**由本次实际涉及的文件决定（后缀表 + 探测器，见各侧正文），不由仓库整体决定。
- **盘工具**：缺哪个先装哪个，否则后面所有"跑绿"都是假的。
- **盘测试**：这是约束一唯一能被观测的手段。记录测试命令与通过率；无测试工程明记「本次只做 A 类，B/C 登记待办」。
- **配置生效探针**（两处都要做）：① 最小探针文件，验工具本身；② **工程内真实文件**，验配置作用到工程上 —— 后者不可省，探针能报而真实文件不报，几乎总是"作用域没覆盖到"。
- **配置遮蔽检查**：`clang-format -style=file -dump-config` 的回显值必须等于 `assets/clang-format` 的取值，不等就是加载了上层目录或用户目录的**另一份**配置。

## 4. P1：现状基线（只读，不改文件、不动配置）

- 文件清单**先落盘、先证明非空**（`[ -s ]` 守卫），**禁用 `$(git ls-files …)` 裸展开** —— 无匹配时参数消失，命令 exit 0、一个文件没查。
- 条数按 **NUL 字节数**统计（清单是 `-z` 产物，`wc -l` 恒为 0）。
- 侧脚本已封装上述纪律：C++ 用 `scripts/baseline_cpp_style.sh`（清单空 / 缺工具 / 缺编译数据库一律非零退出），C# 用 `scripts/bootstrap_dotnet_style.sh`。
- 编译数据库**只覆盖它那一个配置**（Debug 扫不到 Release / ARM64 / `#ifdef` 关掉的分支）—— 基线必须注明"单一配置下"。
- 基线阶段**禁上** `-Werror` / `-warnaserror`：一个让构建整体失败、一个让构建中途断掉，都会产出"看着完整其实被截断"的数字。

## 5. P2：回滚点 → 安装 → 对照实验 → 可信基线

1. **先建回滚点，再动配置**（顺序不能反）。
2. 安装配置：C++ `scripts/bootstrap_cpp_style.sh --fix`（只新增不覆盖）；装完**让工具把模板真读一遍**（`clang-format -dump-config` 的 stderr 必须为空）。
3. **对照实验是本阶段唯一不可省的一步**：往工程里注入已知违规（格式 / 命名 / 警告各一处），确认**真的报出来**。
4. 重跑同一批基线命令得**可信基线** —— 此后所有"前后对比"的分母都是它，不是 P1 的现状表。

## 6. P3：分层整改（核心阶段）

### 6.1 顺序

```
格式（A 类） → 命名 → 语言与设计约束 → 设计粒度 → 注释与文档
```

不能跳到"命名"就先做"设计粒度" —— 粒度整改会改文件结构，之后所有 grep 类统计失效，前面的数字全部作废。

### 6.2 每一层都走同一套流程

1. 从可信基线取出本层的类与处数；
2. **逐处问**：这处改动是规则要求的吗？→ 不是 → 不改（约束二）；
3. 给每处定级 A / B / C —— 带"更现代 / 更地道"理由的一律**先按 B 类**；
4. 按级交付（下表）；
5. **重跑与取基线逐字相同**的命令，出前后数字（命令不同则分母不可比）;
6. 每处挂上缺陷编号（`CPP-nn` / `#nn`）—— 挂不上的，回第 2 步重问。

### 6.3 A / B / C 各自的交付方式

| 类 | 交付方式 |
|---|---|
| **A 定义等价** | 批量，**单独一次提交**，提交信息写"纯格式 / 无行为变更"。闭合判据是两条：① 格式检查命令**无输出**（`clang-format --dry-run --Werror` / `dotnet format --verify-no-changes`）；② 构建通过、测试通过率与 P0 记录一致。**`git diff -w` 只作辅助，不作门槛** —— 格式化几乎必然让它非空，拿它当门槛等于永不闭合 |
| **B 上下文相关** | **先跑 P0 的测试命令**；测试碰不到的文件 → 先补表征测试（把当前行为固化成断言）再改；补不了 → 降回只做 A 类 |
| **C 必然改行为** | **单列提交 + 告知用户 + 有回归测试**，三者缺一 → 登记待办，不当场改。典型：C++ 加 `explicit` / 虚析构（**ABI**）/ `noexcept` / `enum class` / 重排 `#include`（见 `change-discipline.md` §1.4.1）；C# 展开 `?.`（getter 调用次数翻倍）/ `.Result → await` / LINQ 化（**延迟求值**）/ 字段 → 自动属性（**序列化契约**） |

**命名类条目（`CPP-31` / `#25`）是三档人工评审项** —— 改它是 A 或 B 类，**不是 C 类**；重命名 public API 另有各侧迁移纪律的 ADR 门槛。

### 6.4 本阶段明令禁止

- **禁止顺手清理**：死代码、未使用参数、"多余"的防御性检查 —— 它们可能是刻意的；清理属 C 类。
- **禁止为消警告加代码**：补 `default:` 掩盖漏 case、成片 `// NOLINT` / `#pragma warning disable`。
- **禁止补同义复述的文档**：规则要求的是类型级设计意图，不是标签存在性。
- **禁止为压行数机械拆函数**：先过 `design-granularity.md` §3.2 的提问清单；允许拆的信号 §3.3、禁止拆的信号 §3.4。
- **禁止把 A 类与 C 类放进同一个提交**；**禁止单个提交大到无法评审**。

### 6.5 每层改完的即时检查

净增行数是**信号不是判定**（`change-discipline.md` §2.4）：一屏小改动净增上百行 → 回 `change-discipline.md` §2.2 逐条对。

## 7. P4：开闸（钩子与 CI）—— 只做只读检查，禁止自动改写源码

| | C++ | C#/.NET |
|---|---|---|
| 格式 | `clang-format --dry-run --Werror` | `dotnet format --verify-no-changes` |
| 语义 | 各侧正文的完整开关集（C++ 为 `cpp-coding-standards.md` §5.1）**再加 `-Werror`**（**不是只有 `-Wall -Wextra`**；`-Werror` 到这里才上） | `dotnet build -warnaserror`（确认 `EnforceCodeStyleInBuild` 已开） |
| 静态 | `clang-tidy -p <数据库>` + `--header-filter`（用工程自己的 `.clang-tidy`） | Roslyn analyzers |

- **分档开规则**：先「正确性 + 安全」，再「性能 + 可靠性」，最后「可维护性 + 样式」；样式类初期限定 suggestion。
- **验收判据**：故意提交一处对照实验用过的违规，**被拦下**。拦不下 = 钩子没生效。
- **禁止为提高通过率放宽阈值**；确需放宽必须写进对应正文的附录 C 变更记录。
- **"达标"的编译器口径**：开发期与 CI 用 clang 口径（`cpp-coding-standards.md` §5.1 的开关集）；交付物若为 MSVC，交付前**另跑** MSVC `/W4 /analyze` —— **两套数字分开报，不互称"达标"**（clang 干净 ≠ MSVC 干净，两套告警集不可互换）。

## 8. P5：交付与验收 —— 交付说明必须有这四件

1. **前后数字**：整改前 / 后多少处、按三档各多少；**分母必须写明是可信基线**，不许混用 P1 现状表。
2. **剩余清单**：哪些没改、为什么（工具不支持 / 三档人工项 / 涉行为变更待确认 / 范围外）。
3. **可复现命令**：别人照着能跑出同样数字（与取基线逐字相同）。
4. **测试结论**：用了 P0 哪条命令、通过率是否一致；无测试工程写明「本次只做了 A 类」。

外加一条硬要求：**每处改动都挂了缺陷编号或规则条目**。完成态的样板：

> 「本次共修正 `CPP-04` 3 处（A 类）、`CPP-19` 1 处（B 类，已补表征测试）；另有 `CPP-03` 2 处需加虚析构，属 ABI 变更（C 类），已单列提交并等用户确认；`CPP-31` 4 处为三档人工评审项，本轮只出清单未改。分母 = 可信基线。」—— 这是完成。
> 「本次按规范做了一轮整改。」—— 这不是完成。

## 9. 假绿与隐蔽变更（速查）

**假绿**：① `-Wall -Wextra` 不是严格集；② `clang-tidy` 默认集极小、`CheckOptions` 空 = 完全没查；③ 不开 `EnforceCodeStyleInBuild` 时构建期**不做** `IDExxxx` 分析；④ 清单空展开（§4 已防）；⑤ 编译数据库单一配置；⑥ 基线上 `-Werror` 截断数字；⑦ clang 干净 ≠ MSVC 干净（§7 口径）；⑧ 配置遮蔽（§3 查法）。

**隐蔽变更**（看着像"更好的代码"）：C++ `enum` → `enum class`（隐式转换消失）、重排 `#include`（宏顺序 / 自包含性 / PCH）；C# LINQ 化（延迟求值）、字段 → 自动属性（反射契约）；"等价"算术改写（`x/2 → x*0.5`、`x<<1 → x*2` —— 溢出 / 负数移位 / 浮点结合律都会让它们不等价）。
