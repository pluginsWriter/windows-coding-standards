# 设计目的：本规范要治什么，以及怎样算治好了

> 版本：v0.1.1 · 2026-09-28（v0.1.1 按 D-1 的裁决，把 G2 的判据补上**第二个条件「有依据」** —— 详见 §3）
> **本文件是目的层，跨语言共享。** C++ 与 C#/.NET 两侧共同引用它。
> **与另两份跨语言判据的分工**：本文件管**动因与目标**（为什么做、做到什么算成），
> `design-granularity.md` 管**代码形状**（臃肿 / 拆碎），`change-discipline.md` 管**改动本身**（改得对不对、改得多不多）。
> 三者不互相顶替：本文件**不写**任何判据细节，只写"为什么"与"算不算成"。

---

## 0. 为什么单列一份

本工程此前**从未把设计目的完整写下过**。它散落在四份计划书里，每份各写一段：
一份写「回应初衷的部分」、一份写「问题定义」、一份写「收敛选择」——
但没有一处把"要治什么病、怎样算治好了"一次说清。

后果不是"少一段散文"，有两条可实测的：

**一、前提从未进入规范本体。** 两侧正文 §0 写的都是**人类团队的选择困难**
（C# 侧：「规则太多、选不出来、噪音淹没信号」；C++ 侧：「没有一个东西在管」）。
而真正触发本工程的前提是 **AI 编程**——这个前提在规范正文里是不可检索的。验收（接入后实测值见括号）：

```bash
grep -c 'AI 编程' SKILL.md README.md references/cpp-coding-standards.md references/csharp-coding-standards.md
# 要求：**四个文件都必须 ≥ 1**（不得只写在目的层自己这一个文件里 —— 那等于没进本体）
# 接入后的实测：SKILL.md 5 / README.md 1 / C++ 正文 3 / C# 正文 3
```

**二、没有目的，"缺口"就无从定义。** 本工程的审计层五道门**全是证伪型判据**
（差异门的 `expected` 只能取自"skill 已有的声明"），
它能回答「已声明的东西有没有失真」，**结构上回答不了「该有的东西有没有」**。
⇒ 除非先有一份文件说清"该有什么"，审计层永远发现不了覆盖缺口。

**本文件的用途**：给上面第二条提供那个"该有什么"，并给全部条款一个共同的动因。

## 1. 前提：本规范的动因是「AI 编程」引入的病

> **这是全文最不该省的一节。** 省掉它，后面所有条款就退化成一份没有立场的风格偏好。

**前提：本规范面向的主要作者不是人，而是"给 AI 下指令的人 + 执行写作的 AI"。**

这不是修辞，它决定了规范的重心。两类作者的产出特征不同：

| | 人类团队写出的不规范代码 | AI 写出的不规范代码 |
|---|---|---|
| 编译 | 常常不通过 | **几乎总能通过**（AI 会先把语法与类型调对） |
| 格式 | 随人而异 | **常常已经合规**（工具与预训练习惯都在推它） |
| 可读性 | 通常能读出意图 | **常常读不出**：命名生涩、注释复述签名、层次过深 |
| 体量 | 随经验波动 | **系统性偏大或偏碎**：倾向"每个概念一个小类型" |
| 防御性 | 在边界处补 | **到处补**：不信任的地方比信任的地方还多 |
| 评审感受 | 「这里不规范」 | **「看起来都对，就是改不动」** |

### 1.1 由此得出的两条推论

**推论一：重心必须放在机器查不到的那一半。**
机器查得到的部分（格式、大小写、部分命名）AI 通常本来就做得不差 ——
把规范写成一长串机器规则，是在**解决一个不存在的瓶颈**。
真正区分"能用"与"改不动"的，是注释的信息量、命名的可读性、拆分的合理性、
以及"这行代码到底该不该存在"：**这些没有工具能报。**

**推论二：机器规则是底线，不是目标。**
⚠️ **不要把它和两侧正文 §2 的「可检查性」元规则混为一谈。** 两者是不同的事：

| | 可检查性元规则（正文 §2） | 本节的立场（§1.1 推论二） |
|---|---|---|
| 管什么 | 一条条款**怎么标等级**：标 MUST 必须**同时**给得出检测命令**且**有依据（官方标准 / 权威文本 / 本工程显式选定并记录）；缺任一项就降 SHOULD，并注明缺的是哪一项 | 一条条款**值不值得写**：机器管不到的地方才是价值所在 |
| 冲突时 | —— | **不冲突**：一条"须人工评审"的 SHOULD 完全可以是最重要的条款 |

⇒ 正确读法是：**可检查性管"不许假装可查"，本节管"别只写可查的"。** 两者不可互相顶替。

## 2. 五个目标

| 编号 | 目标 | 性质 | 类型 |
|---|---|---|---|
| **G1** | 治「AI 编程」引入的病 | 业务 | 达成为止 |
| **G2** | 约束力 ≈ 可检查性 | 元规则 | 恒为真 |
| **G3** | Windows 平台 / 默认 C++ / 兼容 C#/.NET / 两侧互不套用 | 定位 | 恒为真 |
| **G4** | 整改不改行为 + 不为规范堆代码 | 硬约束 | 恒为真 |
| **G5** | 审计层能发现规则层缺口 | 机制 | 达成为止 |

「性质」三种取值的含义：**业务** = 这是一开始要解决的问题；**元规则 / 定位 / 硬约束** = 做法上的自我约束，
它们不解决 G1，但**违反它们会让 G1 的成果失去意义**；**机制** = 保证 G1 的成果不悄悄退回。

**五个目标不是并列的清单，是有向的**：G1 是目的，G5 是防复发，G2/G3/G4 是手段的边界。
⇒ **做完 G2/G3/G4 不等于做到了 G1。** 这是本工程最容易发生的一次自我误判。

## 3. 各自的达成判据

**判据两条路：机器可查的给命令，不能机器查的必须显式写"须人工评审"。**
不允许出现"看起来能验、实际验不出"的判据 —— 那比没有判据更坏。

### G2 · 约束力 ≈ 可检查性

| 项 | 内容 |
|---|---|
| 判据 | 两边正文里每一条 **MUST**，都指得到一个**唯一权威**（配置模板 / 正文表格 / 缺陷目录条目），给出**一条可执行的检测命令**，**并且**它的取值 / 判据**有依据**（官方标准 / 权威文本 / 或本工程显式选定并记录在案）。缺「可检查」→ 降 SHOULD + 注明"须人工评审"；缺「有依据」→ 降 SHOULD + 标 `[待工程校准]` |
| 机器可查部分 | 权威归属与检测命令的存在性；**取值只有一处**（自检第 21 节：模板恰好声明那些阈值键、正文 / 摘要 / 判据层不得复制数值）；配置取值与正文的一致性；模板可被工具读入 |
| 须人工评审部分 | "检测命令是否真的能验证那条条款" —— 命令存在不等于有效 |
| 已知失真项 | **不写在本文件**。它们随版本变化，登记在两侧正文的附录 D 与当日计划里；本文件只要求"失真被登记且被跟踪" |

### G3 · 平台定位与隔离

| 项 | 内容 |
|---|---|
| 判据 | ① 语言由**本次实际涉及的文件**决定，不由仓库整体决定；② 两侧的配置载体、检查 ID、命名载体、注释语法**互不套用**；③ 同一事实的两份副本里，只有一份是权威 |
| 机器可查部分 | 全部可机查：语言判定的后缀表与探测器逐项一致；两侧配置键不互相污染；缺陷编号不跨侧；跨语言项的取值两侧一致 |
| 须人工评审部分 | 无（本目标是本工程机械程度最高的一条） |
| 反面判据句 | **给 C++ 代码跑 `dotnet format` = 已经跑错了一侧。** |

### G4 · 两条硬约束

| 项 | 内容 |
|---|---|
| 判据 | 整改**不得改变原有行为**（改前能观察到的，改后必须一模一样）；**不得为满足规则而增加代码**（新增的每一行都必须被某条规则指名要求，删掉它就违反那条规则） |
| 唯一出处 | `change-discipline.md`（本文件**不复制**它的 A/B/C 分级与违规清单） |
| 机器可查部分 | 净增行数信号（`git diff --numstat`，只报警不判罪）；"格式改动与逻辑改动是否在同一提交"可由提交粒度核对 |
| 须人工评审部分 | 主体：每处改动的定级、每行新增的归因 |
| 为什么它是硬约束而非建议 | 因为 G1 的病（§1）会让"整改"看起来很像"改善"，而实际上把可读性换成了一堆新代码 |

### G1 · 治「AI 编程」引入的病（**业务目标**）

| 项 | 内容 |
|---|---|
| 判据（前半，机器可查） | **两侧各**存在一张**病灶索引**：每一类 AI 病灶都写明"特征形态 / 机器能否拦住 / 本侧由哪一条对付它"；**前两列逐行一致**（那是"病"本身）；**第四列的归属能在该侧缺陷目录或判据文件里检索到**；指不出归属的行必须明写「本侧不治」 |
| 判据（后半，须人工评审） | **探针测试**：拿一个**从未见过的** AI 生成样本（不在夹具里），加载 skill 后看能否自行说出"这属于哪一类、由哪一条对付、机器拦不拦得住" |
| 机器可查部分 | **自检第 20 节机械核对**：两张表都存在、行数相同、前两列逐行一致、第四列每行都有可检索到的归属或明写「本侧不治」 |
| 须人工评审部分 | 探针测试本身（这是 G1 的真正判据，机器可查的那半只是必要条件） |
| 为什么不能只看前半 | 索引表可以逐行填满却仍然治不了病 —— **表是索引，不是疗效** |

### G5 · 审计层能发现规则层缺口（**机制目标**）

| 项 | 内容 |
|---|---|
| 判据 | 当规则层**退化**（某侧悄悄弃用一份共享判据、某条条款的引用断了、某侧的缺陷目录少了已声明的一类）时，**审计层自己报出来**，而不是等人发现 |
| 现有五道门为什么做不到 | 它们全是**证伪型**判据：`expected` 只能取自"skill 已有的声明"。声明被删掉之后，门就无话可说 —— **声明没有的东西，门看不见** |
| 机器可查部分 | 可构造为**负向注入测试**：故意删掉一处规则层内容（例如一侧正文里对共享判据的引用），看审计层是否 FAIL 并指名 |
| 须人工评审部分 | 判断"报出来的东西是不是真缺口"（假阳性判定） |
| ⚠️ 前置条件 | **必须先有 G1 那张索引**。没有"该有什么"的清单，任何审计层都只能证伪、不能补缺 |

## 4. 总判据（判"设计目的达成"的唯一一句话）

> 加载本 skill 的 agent，面对**第 N+1 种**（从未见过的）AI 生成形态时，
> 能不能**自行说出**"这属于哪一类病灶、规范里由哪一条对付它、机器拦不拦得住"；
> 以及，当规范自身漂移时，**审计层能不能自己发现并指出缺哪一条**。
> **两条都成立 = 设计目的达成。**

两条分别是 G1 与 G5 的判据，且**没有替代品**：
- 只做 G1 不做 G5 ⇒ 索引会随版本漂移而失效，且没人会知道；
- 只做 G5 不做 G1 ⇒ 审计层能精确地报告"我没有任何缺口"，因为它没有缺口清单可比对。

**当前达成状态不写在这里** —— 它随每次改动变化，登记在 `SKILL.md` 的「本版的状态声明」与当日工作记录里。

## 5. 本规范不承诺什么（边界）

写下来是为了防止范围膨胀 —— 一个没有边界的规范会变成"所有代码意见"的集合。

- **不承诺覆盖全部代码质量问题。** 只覆盖 §1 那张表里的形态与该侧缺陷目录里**已登记**的类别。
  目录里没有的，要么是新发现的缺口（应登记），要么是范围外（应明说不管）。
- **不承诺全部机器可查。** 做不到的必须显式写"须人工评审"，**不假装能查**。假装的表现形式是给一条人工判据配一条恒真的命令。
- **不承诺替代代码评审。** 它给评审者一份清单与一致的判据，不替评审者下结论。
- **不承诺改变语言、框架或架构选型。** 规范管"怎么写"，不管"写什么"。
- **不承诺"跑过工具即达标"。** 工具只覆盖机器能看的那部分（见 §1.1）。

## 6. 与其它文件的分工（读错就是读错了一份）

| 文件 | 管什么 | 什么时候读 |
|---|---|---|
| **本文件** | 为什么做、做到什么算成 | 想改动规范本体时**先读它**；判断"要不要加一条规则"时用它当尺子 |
| `design-granularity.md` | 代码的**形状**：臃肿 / 过度拆分 | 遇到超大类型、碎片化、要不要拆的问题时 |
| `change-discipline.md` | **改动本身**：改得对不对、改得多不多 | **接入存量工程之前必读** |
| 两侧正文 | 本侧的全部规则与检测命令 | 写 / 改 / 评审该侧代码时 |
| 两侧缺陷目录 | 本侧的逐类排查清单（编号） | 排查与整改时逐类过 |

**一条读法上的纪律**：本文件**不含**任何阈值、词表、检查 ID、命令。
若你在这里读到了具体取值，那是漂移，应当移除。
