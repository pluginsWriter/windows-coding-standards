# 变更纪律：改得不改行为，加得不堆代码

> 版本：v0.1.0 · 2026-09-28
> **本文件是判据层，跨语言共享。** C++ 与 C#/.NET 两侧共同引用它。
> **分侧陷阱与检测命令分语言** —— 本文件给判据、分侧陷阱表与"该由谁检查"的索引。
> 与 `design-granularity.md` 的分工：那份管**代码的形状**（臃肿 / 拆碎），本份管**改动本身**（改得对不对 / 改得多不多）。

---

## 0. 为什么单列一份

两条约束分别管整改的两个阶段：

| 阶段 | 约束 | 违反后的伤害 |
|---|---|---|
| **接入之前**：整改存量不规范代码 | **不得改变原有行为** | 逻辑被悄悄改掉，测试没覆盖到 → 事故，而责任人以为"只格式化了一下" |
| **接入之后**：新代码与持续整改 | **不得为满足规则而增加代码** | 代码越改越多、间接层越改越厚 → 规范从"降低维护成本"变成"制造维护成本" |

**这两条是同一个病的两个方向**：一条管「改坏了」，一条管「改多了」。
两侧正文的迁移纪律（C# §8 / C++ §9）都只写了**流程**（分档推进、格式与逻辑分提交），**没有给出判据** —— 判据写在这里。

> **前提：规范是判据，不是任务清单。**
> 规则回答「这样写合格吗」，**不回答「必须新增什么」**。
> 把规则当任务清单执行，必然产出没人要的样板代码 —— 那不是合规，那是用规范的名义制造负债。

## 1. 第一条：整改不得改变原有行为

### 1.1 唯一判据

> **整改前能被观察到的，整改后必须一模一样。**
> 做不到「一模一样」，就必须**让用户知情**，单独交付、单独验证 —— 不得混在「顺手改规范」里。

判据落在**可观察**上，不落在「代码看起来差不多」上。§1.3 给出「可观察」的清单。

### 1.2 三类整改必须分开对待（**最容易混的一处**）

| 类 | 定义 | 例子 | 处理 |
|---|---|---|---|
| **A 定义上等价** | 标准保证两种写法语义相同 | 缩进 / 空行 / `(int)x` → `static_cast<int>(x)` / 补命名空间前缀 / C# 的 `""` ↔ `string.Empty` | 可批量做，单独提交，跑构建 |
| **B 上下文相关** | 多数情况等价，**但存在不等价的情形** | `auto` → 显式类型 / `T x;` → `T x{};` / `?.` 的展开 / `int` ↔ `size_t` | **必须跑测试**；无测试则先补表征测试（§1.5） |
| **C 必然改变行为** | 修的就是行为本身 | 删空 `catch` / `.Result` → `await` / `async void` → `async Task` / 加 `explicit` / 加虚析构 / 加 `noexcept` | **必须单列提交、必须告知用户、必须回归**；不得夹带 |

**C 类不是「不该改」，是「改了要认账」。** 空 `catch` 吞异常本身就是缺陷，修它必然让原本被吞掉的异常抛出来 —— 那正是修复的目的，但**调用方可能因此崩**，所以它属于「行为变更」，不属于「格式化」。

> ⚠️ **最常见的越界**：把 C 类混进 A 类的批量提交。评审者看到的是一个「纯格式提交」，里面躺着三处被删掉的空 `catch`。

### 1.3 「行为」包含什么（八项，缺一项就不算「没改行为」）

| # | 项 | 为什么容易漏 |
|---|---|---|
| 1 | 返回值、异常类型与错误码 | 最明显，也是唯一被测试普遍覆盖的一项 |
| 2 | **副作用的顺序** | 两个赋值换序结果相同，但日志顺序、文件写入顺序不同 |
| 3 | **资源释放时机** | `using` 块边界、RAII 作用域、`std::endl` 的 flush 时点 |
| 4 | 并发与线程语义 | `await` 之后的线程、锁的粒度、`volatile` / `atomic` 的增删 |
| 5 | 数值与类型 | 隐式转换、整型提升、有符号/无符号、浮点精度与结合律 |
| 6 | **未定义行为变成定义行为（或反之）** | 这类「修复」看起来是好事，但**结果会变** |
| 7 | ABI / 二进制接口 | 加虚函数、加虚析构、改类布局、改 `enum` 底层类型 |
| 8 | 对外可观测的文本与格式 | 日志文本、序列化字段名、异常消息 —— 下游可能正在解析它 |

> **第 6 项最反直觉**：把「依赖未定义行为但一直能跑」的代码改成有定义的行为，**是行为变更** —— 输出可能不同。这类改动有价值，但必须单独提交。

### 1.4 分侧陷阱表（**两侧不通用，不得互抄**）

左列只在 C++ 侧成立，右列只在 C#/.NET 侧成立。「类」栏用 §1.2 的 A / B / C。

| # | C++（`.clang-format` / `clang-tidy` 整改时） | 类 | C#/.NET（`dotnet format` / 分析器整改时） | 类 |
|---|---|---|---|---|
| 1 | `auto n = v.size()` → `int n = v.size()`：**引入窄化**，是行为变更（`-Wconversion` 抓得到） | B | `var` → 显式类型：一般等价；但改写时写错接口类型会改变重载决议 | B |
| 2 | `T x;` → `T x{};`：对非类类型从「不初始化」变成零初始化 | B | `x?.F()` 展开成 `if (x != null) x.F()`：**若 `x` 是属性，getter 由调用 1 次变 2 次** | C |
| 3 | `(int)x` → `static_cast<int>(x)`：**定义上等价，属 A 类**。但原转换若依赖 `const_cast`，只写 `static_cast` 会**编译失败**（不是静默改语义） | A | `!`（null-forgiving）：**纯编译期断言，运行时零开销，不改变行为** | A |
| 4 | 加 `explicit`：**调用方的隐式转换不再编译** —— 对 API 使用者是行为变更 | C | `?.` 改成 `!` 后直接解引用：从「短路」变成「必定求值」 | C |
| 5 | 加虚析构 / 加第一个虚函数：**vtable 布局改变 = ABI 变更**（具体影响依 ABI 与工具链） | C | `record` → `class`：**相等性语义改变**（值相等 → 引用相等） | C |
| 6 | 加 `noexcept`：改变 `terminate` 行为，且改变容器扩容时选 move 还是 copy | C | `.Result` / `.Wait()` → `await`：线程归属与异常包装（`AggregateException` vs 原异常）全变 | C |
| 7 | `const` 加到成员函数：**改变重载决议**（与非 const 重载并存时调用点会换一个） | C | `using` 块 ↔ `using` 声明：**释放时机改变** | B |
| 8 | **调整成员声明顺序**（初始化顺序由声明顺序决定，成员互相依赖时行为变更） | C | `catch {}` 补日志：**多了副作用，且被吞的异常仍被吞** —— 修与不修都是行为决策 | C |
| 9 | `std::endl` → `'\n'`：**flush 时点改变** | B | `x.CompareTo(y) == 0` ↔ `x == y`：前者用当前区域性，后者是序号比较 | C |
| 10 | `switch` 补 `default:`：**掩盖「漏了一个 case」的警告** —— 为消警告降低安全性 | B | 删除空 `catch`：被吞的异常开始向外抛 —— **这是修复的目的，但调用方可能因此崩** | C |
| 11 | **重排 `#include`**：include 顺序在 C++ 里可能有语义（宏定义、隐式依赖）—— 这是格式化器唯一有真实风险的自动动作，见 §1.4.1 | B | `async void` → `async Task`：异常传播路径改变（`async void` 抛到同步上下文） | C |
| 12 | `enum` → `enum class`：**隐式转换消失**，调用方编译失败；底层类型也可能变化 —— 这是最常见的"现代写法"整改，也是最常见的编译破坏 | C | `(int)x` → `Convert.ToInt32(x)`：**舍入规则不同**（截断 vs 银行家舍入）—— 结果会不一样 | C |
| 13 | "等价"算术改写：`x / 2` → `x * 0.5`、`x << 1` → `x * 2`、`++i` ↔ `i++`、`std::pow(x, 2)` → `x * x`。整数溢出、负数移位、浮点结合律都会让它们**不等价** | B | `foreach` → LINQ（`Where`/`Select`）：**延迟求值** —— 执行时机、异常时机、多次枚举全变 | C |
| 14 | 把 `#include` 从 `.h` 挪到 `.cpp`（IWYU 整改）：可能暴露原本靠传递包含才成立的依赖，也可能**改变可见的声明集合** | B | 字段 → 自动属性：**改变序列化与反射契约**（`XmlSerializer` / `JsonSerializer` 对字段与属性的处理不同） | C |
| 15 | 宏 → `constexpr`：宏是**文本替换**，没有类型、没有作用域、参数可能被求值多次；替换后求值次数与作用域都会变 | B | `IEnumerable<T>` → `List<T>`（或反向）：既改 API 表面，又改求值时机与内存行为 | B |

> **用法**：拿不准某处改写属于哪一类时，先在这里找。**找不到就按 B 类处理（跑测试），不要默认它是 A 类。**

> ⚠️ **第 12–15 行的共同规律**：真正危险的整改不是"格式化"，而是**以"现代写法"为名的等价替换** —— `enum class`、LINQ、`constexpr`、自动属性、算术化简。它们看着更像"更好的代码"，所以评审者最不设防，而它们恰恰会改行为或破坏调用方。
>
> **判据**：任何带"这样更现代 / 更地道 / 更简洁"理由的改写，**默认按 B 类处理**（跑测试），能举出标准或文档证明"定义上等价"的才降为 A 类。

#### 1.4.1 `#include` 重排：C++ 侧唯一「格式化就会动语义」的动作

`clang-format` 的 `SortIncludes` / `IncludeBlocks` 会把 `#include` **排序与分组**。多数工程里它无害，但 C++ 的 include 顺序**不是纯风格**：

- 头文件之间的宏定义顺序可能有影响；
- 「先包含自己的头」这一惯例本身是为了**暴露缺失的自包含性**，重排会掩盖它；
- 预编译头（PCH）与 `#pragma once` 的交互依顺序而定。

**因此本规范的要求是**：

1. **`SortIncludes` 与 `IncludeBlocks` 必须在 `.clang-format` 里显式写死**，不得依赖预设默认 —— 否则同一份配置在不同版本的 clang-format 上产出不同结果，而「格式提交」本来承诺无行为变更。
2. 模板当前取**保守值**（不自动重排 include）。这与本规范「人工排版同等有效」的立场一致：**唯一有语义风险的自动重排，默认关掉。**
3. `[待实测]`（本机无 clang-format）：实际生效值需核对 ——
   ```bash
   clang-format -style=file -dump-config | grep -E 'SortIncludes|IncludeBlocks'
   ```

### 1.5 证据阶梯：怎么证明「没改行为」

**按下表从强到弱，取能拿到的最强一条。**

| 级别 | 证据 | 适用与边界 |
|---|---|---|
| 1 | **有测试，跑过，通过** | 唯一算证明的。但**测试没覆盖到的行为，跑绿也不代表没改** |
| 2 | **`git diff -w` 为空** | 只证明「改动仅涉空白」→ **充分条件，可闭合**；非空**不是**「改坏了」的证据 |
| 3 | **改之前先看格式化器会做什么** | `clang-format -style=file -dump-config` / `dotnet format --verify-no-changes`（只读） |
| 4 | **表征测试**（无测试时先补一个） | 把当前行为**原样固化**成断言，再改；断言仍过 = 行为未变。**这是没有测试时的标准做法** |
| 5 | **逐处人工确认 + 明确告知用户** | 最低一级。**必须写进交付说明**，不得默认已验 |

**C 类不允许停在 5 级。** 至少要有一个能复现的回归测试；否则应把缺陷登记进待办，而不是当场改掉。

> 构建期证据在两侧正文：C++ 侧 §7.1 的四道闸门、C#/.NET 侧 §7.1。

### 1.6 提交结构：一次变更只做一件事

- **A 类批量做**，单独一次提交；提交信息写明「纯格式 / 无行为变更」。
- **B / C 类单列**，每类（甚至每处）一次提交，提交信息写明**改了什么行为**。
- **严禁**把 A 类与 C 类放进同一个提交。
- **禁止「顺手清理」。** 乱码注释、死代码分支、未使用的参数、空实现、注释掉的旧代码、"多余"的防御性检查 —— 这些**看起来都是垃圾，实际上可能是刻意保留的**：ABI 占位的保留字段、平台桩、上游接口的占位参数、调试开关、被 `if (0)` 保留下来的参考实现。
  **清理它们属于 C 类**，不是一个"格式提交"该做的事。判据同 §2.1：**改它的理由必须是某条规则要求，不是"看起来没用"。**
- **单个提交的规模要小到能被评审。** 一次 3000 行的"格式提交"事实上不会被任何人读完 —— 那不是提交，那是把评审责任推给别人。规模大的整改拆成多次提交，每次一个清晰主题。
- 大范围整改前留**回滚点**（干净分支或 tag），否则「改坏了」就没有「改回去」。

> **判据只有一条：评审者能否只看提交信息就判断「这次要不要重点看行为」。**
> 两侧正文的「格式与逻辑不得同提交」红线是本条的落地形式，本文件不重复它的措辞。

### 1.7 整改的完成定义（DoD）：三件东西，缺一不算完成

| # | 必须给出的东西 | 反面（不算完成的样子） |
|---|---|---|
| 1 | **前后数字**：整改前有多少处违规、整改后有多少、分类各多少 | 「已经改好了」——没有数字就无法复核，也无法判断"没改的"是漏了还是有意为之 |
| 2 | **剩余清单**：还有哪些没改、为什么没改（工具不支持 / 属三档人工项 / 涉及行为变更待确认 / 范围外） | 「全部完成」——通常意味着只是把格式化器跑了一遍 |
| 3 | **可复现命令**：别人照着能自己跑出同样的数字 | 只给结论不给命令 —— 那这个数字就是不可核验的 |

**另有一条硬要求**：**每处改动都要能对应一个缺陷编号或规则条目。**

> 「本次共修正 `CPP-04` 3 处、`CPP-19` 1 处，另有 `CPP-31` 2 处因涉及行为变更（C 类）待确认」—— 这是完成。
> 「本次按规范做了一轮整改」—— 这不是完成，这是把判断责任推回给用户。

**为什么这条单列**：前面 §1.1–§1.6 讲的都是"改的时候别出事"，本节讲的是"改完之后交付什么"。**没有这一节，"整改"就变成一件无法验收的事。**

## 2. 第二条：不得为满足规则而增加代码

### 2.1 唯一判据

> **新增的每一行，必须能指着一条规则说「是它要求我加的」，且删掉这行就违反那条规则。**
>
> 说不出 → 这就是为规范而加的代码，删掉。

三条推论：

1. **规则是合格判据，不是新增清单。** 「格式要统一」不要求新增任何一行。
2. **「更规范」本身不是新增代码的理由。** 只有某条规则**明确要求**某个结构存在时，新增才有正当性。
3. **新增的代码同样要过本规范。** 为满足规则加进来的样板，如果自己就臃肿、就没有独立变化原因，那是**用规范制造违规**。

### 2.2 常见的「为规范而加」（**清单，不是穷举**）

| 加的东西 | 为什么违规 |
|---|---|
| **复述签名的文档注释**（`@param x 传入 x`、`<summary>Gets the name</summary>` 加在 `Name` 上） | 规则要求的是**类型级设计意图与不变式**，不是标签存在性。同义复述既满足检查、又零信息量 —— 规范自己制造的假达标 |
| **只为消掉魔法数而提取、且只用一次的常量** | 名字比字面量更难懂时可读性是净减。判据见下 |
| **给每个字段补属性 / getter+setter** | 规则禁止的是**公开字段**，不是要求你把每个字段包装一遍 |
| **为「可测试性」加的无状态转发层** | 见 `design-granularity.md` §3.4 |
| **为压行数强行拆出的碎片** | 同上，判据在其 §3.1 |
| **`///` / `/** */` 铺到每个私有成员** | 规则要求的是公开接口与类型级说明；私有成员靠命名说清 |
| **大段 `#pragma warning(disable:…)` / `// NOLINT` 豁免** | 不是「加代码」但同类：**用噪音换绿色**。豁免必须有理由、有范围、有到期条件 |
| **「防御性」参数校验加到内部函数** | 跨到 §1 —— 它**改变行为**（原本合法的调用会开始抛异常） |
| **把 `switch` 换成注册表 / 查表 / 多态** | 为消除一个 30 行的 `switch` 引入 4 个类型。除非有 `design-granularity.md` §3.3 的独立变化原因 |
| **为凑齐「每个公开成员都有测试」而写的空断言测试** | 测试里只有 `Assert.NotNull(x)` 或 `EXPECT_TRUE(true)`。它让覆盖率数字好看、让评审清单打勾，**但没有验证任何契约** —— 而且它自己就是新增代码 |
| **把代码搬到新文件，职责没变** | 文件数增加了，可理解性没有改善。拆分的判据是变化原因，不是"分开放" |

**魔法值的正确判据**（比「提取常量」更该先问）：

> **这个字面量的含义，能否从它的使用位置一眼读出？**
> - `circle(r, 3.14159)` → 能读出，**不必提取**；
> - `sleep(86400000)` → 读不出（毫秒？天？）→ **必须提取**，且名字要带单位：`kSessionTimeoutMs`。
>
> 提取的价值在**命名带来的含义**，不在「消灭了字面量」。

> ⚠️ **「不增加代码」不等于「可以删代码」。** 删代码同样是**改变行为**，归 §1 管。两条约束不是"少写多删"的意思 —— 是"只做规则要求的那一件事"。

### 2.3 正当新增（**这些不算「为规范而加」**）

- **类型级设计意图注释**（`design-granularity.md` §5 要求的三件事）—— 它承载规则查不出的信息；
- 为「能说出独立变化原因」的新职责而拆出的单位（判据在其 §3.1）；
- 修复**真实缺陷**所需的最小改动（哪怕是新增，例如补一个漏掉的释放）；
- **表征测试**（§1.5）—— 它是改动的证据，不是产品代码。

### 2.4 净增行数：一个信号，不是判定

整改**天然是净删或持平**的：规范不生产功能，只删冗余、改名、调序。

```bash
# 一次整改（工作区全部改动）的净增行数：负数或接近 0 = 正常
git diff --numstat | grep -E '^[0-9]' | awk '{ a += $1; d += $2 } END { printf "净增 %d 行（+%d / -%d）\n", a - d, a, d }'
```

**怎么读**：

- **净增 ≈ 0** —— 格式类改动（增删成对），正常。
- **净增为负** —— 删冗余，正常；反而应当问「删掉的是哪些」。
- **净增为正且显著**（例如一屏小改动净增上百行）—— **回到 §2.2 逐条对**。
  ⚠️ 这**不是违规判定**：补文档、拆职责都会净增，判据仍是 §2.1 那句话。

> ⚠️ `--numstat` 对**二进制文件**输出 `-`，故必须先用 `grep -E '^[0-9]'` 滤掉，否则 awk 会把 `-` 当字符串参与相加。

### 2.5 与 `design-granularity.md` 的分工

两个文件都通向「代码总量失控」，但**入口相反**：

| | `design-granularity.md` | 本文件 §2 |
|---|---|---|
| 管什么 | **代码的形状**：一个类型 / 函数该不该拆 | **改动本身**：一次整改该不该新增 |
| 典型错误 | 把 800 行硬拆成 13 个碎片 | 为了「更规范」加出没人要的样板 |
| 判据 | 拆出的每个单位是否有独立变化原因 | 新增的每一行是否被某条规则指名要求 |

**两者必须同时生效**：只防拆不防加 → 代码膨胀；只防加不防拆 → 结构失控。

## 3. 一次整改的正确形状

```
先判定语言（scripts/detect_language.sh）
   ↓
只读采基线（数出会改多少处）—— 两侧正文的评审步骤
   ↓
逐处问：这处改动是规则要求的吗？ → 不是 → 不改（§2.1）
   ↓
给每处改动定级：A / B / C（§1.2）—— 带"更现代 / 更地道"理由的一律先按 B 类
   ↓
├─ A 类 → 批量，单独提交，跑构建
├─ B 类 → 跑测试；无测试 → 先补表征测试（§1.5）
└─ C 类 → 单列 + 告知用户 + 有回归测试；做不到 → 登记待办，不当场改
   ↓
每处改动挂上缺陷编号（CPP-nn / #nn）—— 挂不上的，回到第一步重问
   ↓
改完看净增行数（§2.4）；显著为正 → 回 §2.2 复查
   ↓
交付说明：前后数字 + 剩余清单 + 可复现命令（§1.7）
```

**最后一条是纪律**：一份「整改完成」的交付，**必须能回答「还有哪里没改、为什么」**。只能回答「全改完了」的，多半只是把格式化器跑了一遍。

> ⚠️ 两侧正文都有「格式与逻辑不得同提交」的红线。本文件不重复它的措辞 —— **判据只有一条：评审者能否只看提交信息判断「这次要不要重点看行为」。**

## 4. 评审清单（可直接用于 code review）

**行为**

- [ ] 本次每一处改动，属 A / B / C 哪一类？B 类的测试在哪？C 类的知情与回归在哪？
- [ ] 有没有把 C 类混在「纯格式」提交里？
- [ ] 带「更现代 / 更地道」理由的改写（`enum class`、LINQ、`constexpr`、自动属性），举得出"定义上等价"的依据吗？
- [ ] 有没有"顺手清理"（死代码、未使用参数、注释掉的旧代码）？那是 C 类，不该混在格式提交里。
- [ ] 副作用的顺序、资源释放时机、并发语义，有没有被波及？
- [ ] 有对外可观测的文本（日志、序列化、异常消息）被改动吗？下游有没有在解析它？
- [ ] 大范围改动前留回滚点了吗？
- [ ] 单个提交的规模能被评审吗？

**增量**

- [ ] 本次新增的每一行，能指出是哪条规则要求的吗？
- [ ] 新增的文档注释，除了复述签名还说了什么？
- [ ] 新提取的常量名，比原来的字面量更容易理解吗？
- [ ] 新增的抽象层有几个实现 / 调用方？（见 `design-granularity.md` §3.2）
- [ ] 新增的测试有没有真的验证一个契约（而不是只有 `Assert.NotNull`）？
- [ ] 净增行数是多少（§2.4）？显著为正的话，逐条对过 §2.2 吗？
- [ ] 有没有为消除一个警告而降低安全性（例如给 `switch` 补 `default`）？

**交付（§1.7 的完成定义）**

- [ ] 给了整改前后的数字吗？
- [ ] 给了剩余清单（还有哪些没改、为什么）吗？
- [ ] 给了可复现命令吗？
- [ ] 每处改动都挂了缺陷编号 / 规则条目吗？

## 5. 检测：哪些能机器化

| 项 | 能否机器化 | 说明 |
|---|---|---|
| 超阈值 / 超行数 | ✅ | 见两侧配置模板 |
| 净增行数 | ✅ 可量，**判定靠人** | §2.4 |
| **是否改变行为** | ❌ **不能判定** | 只能靠测试、`git diff -w` 与人工分级（§1.5） |
| 新增代码是否有规则依据 | ❌ | 语义 |
| 提交是否混合了 A 与 C 类 | ⚠️ 只能提示 | `git show --stat` 看规模；判定靠人 |

**唯一能机器化的「行为不变」证据是 `git diff -w` 为空** —— 它只覆盖「仅涉空白」这一种情形，其余一律要人判。
