# C++ 大类拆解：职责、方法契约与行为不变的操作指引

> 适用：现有 C++ 类型或实现文件过大、职责混杂，且用户要求在不改变功能的前提下整改。**不是**自动拆分指令；文件体量触发口径见 `cpp-coding-standards.md` §5.4，是否拆按 `design-granularity.md` §3 判断。变更分级与行为边界仍以 `change-discipline.md` §1 为准。本指引尚未通过真实工程的完整拆解演练，不可将文档存在等同于已验证能力。

## 1. 先判定要拆的是文件还是类型

- 先区分一个长文件包含单一类型、多个类型、自由函数、平台分支或重复生成代码；检查已有按功能分开的 `.cpp`。文件长不自动等于类大，已分文件不自动等于已拆职责。
- **仅分文件**：同一类型的成员定义移到不同翻译单元，类型职责、公开接口及对象布局不变。改善定位，但不宣称已拆解类。
- **职责拆解**：新单元承担能独立变化的操作/状态，并说清谁创建、拥有、释放，以及与原类型的协作。不能为凑行数新建 `XxxHelper` 或无状态单方法类。
- 对每个候选写出「当 X 变化时，只需改这里」，且盘点方法调用者、共同读写的状态、不变量、资源、外部 API 与跨文件依赖。共享可变状态没有明确归属时，暂不抽类型。

**拆解前产物：逐候选填写映射表**（不要求把内部清单写成新增源码）：

| 原入口/方法 | 调用方与可观察结果 | 读写状态/不变量/资源 | 改后归属与变化原因 | 外部接口保留方式 | 风险与证据 |
|---|---|---|---|---|---|
| 每个候选职责簇至少一行；无法核实填「待核实」，不得猜测 | 包含公共调用方及跨职责调用 | 标明唯一所有者、初始化与释放时点 | 仅分文件 / 新类型 / 保留原类，并说明为何 | facade、签名、布局或不适用 | 测试、配置、未覆盖路径 |

表中要能从每个公开入口追到原有实现与改后实现；漏掉的状态、调用方或宏分支先补盘点，再动代码。对外 API 必须保持时，允许原类保留薄 facade，但要说明这个转发承担的**兼容性职责**；内部无意义的层层转发应合并。

## 2. 同时防臃肿和防过碎

每个新单元检查：是否有独立变化原因、清晰的状态/资源所有权及不变量、不同于原类的契约。不能回答三者中的关键项，就不以「更短」为由拆出类型。反过来，文件未超预警但类型混合互不相关的变化原因，也要审查职责蔓延。

拆后对照改前：新增了多少类型/文件/转发跳转？一次典型调用是否必须跨更多文件拼接才能理解？是否需要把同一可变状态来回传递、引入双向依赖，或者原类型与新类型经常必须一起修改？出现这些信号时考虑保留同类成员、用私有函数/命名空间组织，或撤回抽取。短文件与单调用方**本身不是违规**，决定依据仍是可理解性和变更边界；正反判据详见 `design-granularity.md` §3。

## 3. 在声明处写能指导调用的 C++ 契约

公开入口和非显然的跨职责方法，优先记录调用者无法从名称/类型推出的信息；私有的一眼可懂方法不强制逐个补注释。C++ 使用 Doxygen（`cpp-coding-standards.md` §6），不是 C# XML。

| 需要解释 | 在方法/类型声明处回答的问题 |
|---|---|
| 目的与边界 | 何时调用？为什么由此类型负责？与相邻类型的分工是什么？ |
| 输入与输出 | 参数方向、单位、范围、缓冲区容量、空值语义；返回值、错误码、异常及部分结果含义是什么？ |
| 生命周期 | 输出内存、句柄、COM 对象由谁释放？在哪个线程/调用序列里有效？ |
| 副作用与时序 | 是否改变缓存、设备状态、日志或枚举顺序？依赖什么初始化/锁？ |

`@param buffer 输出缓冲区` 是复述；`@param buffer 调用方提供，长度至少为 capacityBytes；失败时内容不保证保持原值` 才是契约（**仅示意，不得未经核实写到具体 API 上**）。对公开边界逐项区分「语法有效」「信息有用」「与实际实现一致」；只写已确认的现有行为，未确认项列入待办，不猜测。宏、平台条件与异常模式可能改变契约时，按实际配置分别核对。类型级意图按 `design-granularity.md` §5；不对所有方法堆同义标签。

## 4. 固定行为边界后逐簇迁移

1. **改前契约**：列出导出函数/公共 API → 原方法 → 共享状态/helper → 外部 API 的调用链。记录 ABI（导出符号、名称、签名、调用约定、结构体布局）、返回/错误码、输出顺序/日志、资源释放时点、线程/缓存语义及相关构建配置。
2. **改前可执行基线**：在目标 Windows 环境记录相关配置的构建、导出符号，以及成功、失败、空结果、边界输入的表征测试；依赖设备或系统状态时固定环境和样本。基线未覆盖的路径明确列出。构建通过只证明能构建，不证明行为不变。
3. **一次迁移一个职责簇**：先保持公共接口/对象布局、调用次序、返回值不变。核对新翻译单元是否进入所需的 `.vcxproj` 配置及 filters、PCH、宏定义与链接依赖；按映射表检查状态所有权和初始化/销毁顺序。不得夹带格式化、错误处理改进或“顺手清理”。
4. **每簇对照**：复查 diff、运行同一配置和测试，比较导出表及可观察结果；差异逐项解释，不以编译成功或函数体未改代替对照。任何公开签名、布局、调用约定或行为改变属于另案，不能藏在「纯拆解」中。

**分级**：移动翻译单元、私有状态与方法通常至少是 B 类（宏、链接、初始化和生命周期可能改变行为）；确有行为/ABI 改变属于 C 类，按 `change-discipline.md` 单列。无改前基线、目标 Windows 工具链或相应覆盖测试时，可以交付设计、仅靠静态证据能成立的判断及待办，**不得宣称功能不变已验证，也不得把 B 类重构交付成已完成整改**。

## 5. 交付检查（判据，不是多造表格的目标）

- 结论分清「仅分文件」「职责拆解」「保留原状」；映射表涵盖方法、状态、调用方和改后归属，并记下未拆的原因。
- 对每个新单元说明独立变化原因与状态所有者；回查新增类型/跳转是否让典型调用更难理解，必要时撤回拆分。
- 方法契约逐项区分已核实、无需额外注释、待核实；核对注释与实现一致，不以 `-Wdocumentation` 无报警代替语义检查。
- 列出改前/改后构建配置、导出/ABI 对照、表征测试和未覆盖路径；缺目标 Windows 验证则标记**未验证**，不能声称功能不变。
- 关联 `CPP-30`、`CPP-32`–`CPP-37` 或规范条款，按 `remediation-playbook.md` §8 交付；不为了表格完整度给源码增加空转发层或同义注释。
